# 확인하고 적기

제 작업 방식을 옮긴 것이다. SoftBank 해커톤 2026(4인 팀, 세 지역 자동 배포)에서 같은 패턴이
반복해서 효과를 냈다 — **추정으로 결론 내지 않고, 틀린 것은 숨기지 않고,
왜 틀렸는지까지 적는다.**

## 1. 적기 전에 찔러본다

"작동한다"를 문서·PR·슬랙에 적기 전에 **실제로 그 경로를 통과시킨다.**

- 설정을 바꿨으면 → 바꾼 결과가 나타나는 지점까지 가서 본다
- "적용됐다" 는 머지했다는 뜻이 아니다. **반영까지 확인한다**
- 측정값을 전달하려면 **무엇부터 무엇까지 쟀는지**를 먼저 고정한다

실패 사례로 기억할 것:

```
"3분 57초 → 1분 43초"      AI 검토 시작 시각부터 쟀다. PR 생성 기준이면 1분 47초
"캐시 넣으면 42초 절약"      실제로는 20초 손해. 빌드가 이미 20초대였다
"응답 검사만으로 충분하다"    100% 고장난 버전을 35% 확률로 놓친다
```

## 2. 틀렸으면 네 가지를 적는다

틀린 것을 발견하면 "고쳤습니다" 로 끝내지 않는다.

| | |
| --- | --- |
| **무엇이** | 실제로 관측된 것. 추정이 아니라 출력·로그·응답 코드 |
| **왜** | 구조 때문인지 운 때문인지. 재현되는지 |
| **얼마나** | 가능하면 수치·확률. "가끔 실패" 보다 "세 번에 한 번" |
| **내가 왜 틀렸나** | 어떤 전제를 검증하지 않고 넘어갔는지 |

네 번째가 핵심이다. 이게 없으면 같은 자리에서 또 틀린다.

```
P(놓침) = (2/3)^6 + 6·(1/3)·(2/3)^5 ≈ 0.35
→ "가끔 안 잡힌다" 가 아니라 "세 번에 한 번 놓친다"
```

## 3. 모르면 모른다고 쓴다

원인을 특정하지 못했으면 **그럴듯한 설명으로 메우지 않는다.**

```
❌ "CI 가 더 최적화돼서 빨라진 것으로 보입니다"
✅ "구간별 기록이 남지 않아 어디서 줄었는지는 특정하지 못했습니다.
    그 사이 의도적으로 바꾼 설정은 없으므로 러너 대기 같은 변동일 수 있습니다"
```

비교할 수 없는 두 숫자를 나란히 놓지 않는다. 조건이 다르면 **조건을 표로 적는다.**

## 4. 숨기지 않고 공개한다

한계와 실패를 **같은 문서 안에** 적는다. 따로 빼거나 찾아 들어가야 보이게 두지 않는다.

- 공개 문서(README·DEMO)에 「아직 못 하는 것」 절을 둔다
- 안전장치를 자랑했으면 **그 안전장치가 놓치는 조건**도 같은 자리에 적는다
- 이미 열린 과제와 **같은 종류의 문제**라면 연결한다

## 5. 기록은 세 군데로 나눈다

| 어디에 | 무엇을 |
| --- | --- |
| **PR 본문** | 무엇을 / 왜 / 어떻게 확인했나 / 되돌리기. 버린 방안과 그 이유까지 |
| **CLAUDE.md 주의** | 다음에 같은 함정을 만날 때 읽을 것. 🔴 로 표시, 재현 명령 포함 |
| **공개 문서** | 심사위원·동료가 읽는 것. 쉬운 말, 코드 용어 대신 비유 |

PR 본문에 **"버린 방안과 그 이유"** 를 남기는 것이 특히 값졌다. 결론만 적으면
나중에 "왜 더 쉬운 길을 안 갔지" 가 반복된다.

## 하지 말 것

- 관측값만 보고 구조를 단정하기 — **"10초 간격이니 폴링이겠지"** 가 틀렸다. 웹훅 구조였다
- 한 환경에서 되는 것을 전체로 일반화하기 — 서울에서 되는 것이 부산에서 안 됐다
- 사과문 쓰기. **틀린 사실과 원인만 적고 넘어간다**
- 수치를 고쳤으면 **그 수치가 들어간 모든 곳**을 같이 고치기 (그림·발표자료·README)

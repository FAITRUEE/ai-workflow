# 문서 ↔ 코드 대조

AI와 일하면 코드는 하루에도 여러 번 바뀌는데, 노션 명세 · 배포 문서는 처음 쓴 날에 멈춰 있기 쉽다.
그러면 팀원도, 다음 작업을 하는 AI도 **낡은 문서를 정본으로 믿고** 일한다.
이 스킬은 문서 한 장을 "지금 코드 기준으로 맞는가"로 한 줄씩 대조한다.

## 원칙

- **기준은 코드다.** 문서와 코드가 다르면 코드가 지금의 사실이다. 단, 코드가 문서의 *결정*을 어긴 것이면 문서가 맞고 코드가 버그다 → 이 경우는 따로 표시한다.
- **근거 없이 "다르다"고 쓰지 않는다.** 어긋난 줄마다 코드 위치(`파일:줄`)나 PR 번호, 커밋을 붙인다.
- **확인 못 한 것은 "확인 못 함"으로 남긴다.** 서버 설정 · 클라우드 콘솔 · 시크릿처럼 저장소 밖에 있는 것은 추측하지 않는다.
- **남의 문서는 고치지 않는다.** 내 담당이 아닌 문서는 어긋난 곳만 정리해 담당자에게 넘긴다.

## 순서

1. **무엇을 대조할지 정한다**
   - 문서의 정본 위치(노션 · 로컬 md)와 버전, 마지막 수정일
   - 대조할 저장소와 브랜치(보통 main 또는 develop). 문서 날짜 이후 머지된 PR 목록을 먼저 본다
     ```bash
     gh pr list --state merged --search "merged:>=YYYY-MM-DD" --limit 30
     ```
2. **문서를 주장 단위로 쪼갠다** — "API 주소는 /api/v1", "배포는 main 푸시 시 자동", "테이블 15개" 처럼 참 · 거짓을 가릴 수 있는 문장으로
3. **주장마다 코드에서 찾는다** — 라우터 · 설정 파일 · 워크플로 · 마이그레이션 · 환경 변수 예시 파일
4. **판정한다**
   | 판정 | 뜻 |
   |---|---|
   | ✅ 맞음 | 코드와 같다 |
   | ❌ 낡음 | 코드가 바뀌었는데 문서가 그대로 (근거: PR · 파일) |
   | ⚠️ 코드가 어김 | 문서의 결정과 다르게 구현됨 → 버그일 수 있음, 사람에게 묻는다 |
   | ❓ 확인 못 함 | 저장소 밖에 있어 볼 수 없음 |
   | ➕ 빠짐 | 코드엔 있는데 문서에 없음 (새 기능 · 새 테이블) |
5. **결과를 보여 준다** — 문서마다 심각한 순서로 표 하나. 맨 위에 한 줄 요약("4개 중 3개가 PR #13~#18을 반영 못 함")
6. **사용자가 고르면 새 버전 원고를 만든다** — 버전 번호를 올리고, 맨 아래 변경 이력에 "무엇을 · 왜(근거 PR)" 한 줄. 노션 반영은 `notion-publish` 방식을 따른다

## 보여 주는 형식

```markdown
## 배포 문서 — 가장 낡음 (노션 v0.4, 09/30)

| 문서 내용 | 실제 (근거) | 판정 |
|---|---|---|
| 리전 서울 | 시드니 — 무료 플랜 제약 (PR #19) | ❌ 낡음 |
| 인증은 GitHub OIDC | 배포 전용 IAM 키 (PR #19) | ❌ 낡음 |
| DB 포트 외부 공개 | 127.0.0.1에만 열림 (compose.prod.yml) | ❌ 낡음 |
| 배포 실패 시 자동 롤백 | deploy.yml에 /health 확인 후 이전 이미지로 | ✅ 맞음 |
| 시크릿 등록 위치 | 저장소 시크릿 0개 — 조직 시크릿일 수 있음 | ❓ 확인 못 함 |
```

## 하지 않는 것

- 문서 문체 · 맞춤법 다듬기 (내용 대조만 한다)
- 확인 없이 문서를 통째로 다시 쓰기
- 다른 사람 담당 문서를 직접 고치기

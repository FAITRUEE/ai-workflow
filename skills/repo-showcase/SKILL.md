# 저장소를 보여 줄 수 있는 상태로

서류에 저장소 링크를 걸면 심사자는 README 첫 화면과 데모 링크 하나만 눌러 본다.
그런데 끝난 프로젝트는 대개 **데모가 깨져 있거나, README 사진이 예전 화면이거나, 아예 사진이 없다.**
이 스킬은 "실제로 돌려 본 것만 보여 준다"는 순서로 저장소를 다시 정리한다.

## 순서

### 1. 먼저 돌려 본다 — 고치기 전에 현재 상태 기록
- 저장소를 최신 main으로 받고, README에 적힌 실행법 그대로 띄운다. **README대로 안 뜨면 그것부터 문제**로 적는다
- 배포 주소가 있으면 그것도 연다
- 데모 · 기능을 사용자가 밟는 순서대로 하나씩 눌러 보고 결과를 표로 남긴다

| 데모 | 결과 | 문제 |
|---|---|---|
| 서명 시뮬레이터 | ❌ | 결과가 한 줄로 뭉쳐 나옴, 예시 입력이 비어 있음 |
| 계보 그래프 | ✅ | 이름이 원과 겹쳐 안 읽힘 (작음) |

### 2. 고친다 — 보여 주는 데 걸리는 것만
- 데모가 안 되는 버그, 첫 화면이 비어 보이는 문제, 글자 깨짐 · 겹침을 우선한다
- 새 기능은 넣지 않는다. 고친 것은 버그 단위로 커밋한다
- 원래 PR로 관리하던 저장소면 **main에 바로 넣지 않고 PR로** 올린다

### 3. 스크린샷을 다시 찍는다
- 고친 뒤에 찍는다. 브라우저 창 크기를 고정하고(예: 1280×800) 모든 장을 같은 크기로
- 데이터가 비어 보이지 않게 예시 데이터를 넣고 찍는다
- **다른 사람 이름 · 이메일 · 토큰 · 내부 주소**가 보이면 흐리게 가리거나 잘라 낸다
- 파일은 `docs/images/` 같은 한 폴더에, 무엇을 찍었는지 알 수 있는 이름으로

### 4. README를 다시 쓴다 — 첫 화면에서 끝나게
1. 한 줄 소개 + 대표 화면 1장 + **바로 써 보기 링크**(데모 · 소개 페이지)
2. 무엇을 하는가 — 기능마다 스크린샷 1장과 두세 줄
3. 구조 그림 또는 기술 스택 표
4. 내가 맡은 부분(팀 프로젝트라면 `contribution-audit` 결과 범위 안에서)
5. 실행 방법 — 1단계에서 실제로 성공한 명령만
6. 한계 · 남은 과제

### 5. 조직 프로필 · 소개 페이지 (있으면)
- 조직 프로필(`.github/profile/README.md`)은 프로젝트 한 줄 소개 · 저장소 표 · 데모 링크만
- 소개 페이지가 있으면 같은 스크린샷과 같은 문장을 쓴다

### 6. 실제 화면에서 확인하고 끝낸다
- GitHub에서 README · 조직 프로필 · 소개 페이지를 직접 열어 사진이 뜨는지, 링크가 살아 있는지 본다
- 사용자에게: 데모별 점검 결과 표, 고친 버그 목록, 바뀐 링크, 아직 못 한 것

## 하지 않는 것

- 돌려 보지 않은 기능을 README에 "된다"고 쓰기
- 팀원이 한 부분을 내 것처럼 쓰기
- 확인 없이 force push · 히스토리 정리

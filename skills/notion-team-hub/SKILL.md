# 노션 팀 공간 세팅 → 점검

iM 아카데미 머신러닝 프로젝트 「눈치」(2026-10, 4인 · 9일) 세팅에서 반복된 흐름을 옮긴 것이다.
모양은 이전 팀 프로젝트(해커톤 · 아카데미 통계 프로젝트)에서 쓰던 노션을 다듬은 것이다.

핵심은 세 가지다. **팀스페이스에 만든다**, **문서는 정해진 몇 개만 짧은 틀로**,
**다 만들면 문서끼리 맞는지 점검하고 고친 건 버전으로 남긴다**.

필요할 때 읽는 파일:

| 파일 | 언제 |
|---|---|
| `references/home-layout.md` | 홈을 만들거나 다시 정리할 때 (전체 마크업 틀) |
| `references/team-access.md` | 팀원을 붙일 때 (내부 통합·권한·검증) |
| `references/slack-notice.md` | 설정법 공지문을 쓸 때 |
| `scripts/verify_notion_integration.py` | 토큰이 무엇을 읽고 쓸 수 있는지 확인할 때 |

## 0. 시작 전에 확인

- **어느 워크스페이스인지 먼저 본다.** 노션 도구가 두 종류 붙어 있을 수 있다.
  - 공식 노션 커넥터(`notion-get-self`로 내 워크스페이스인지 확인)를 쓴다.
  - 다른 팀의 내부 통합 토큰으로 붙은 `mcp__notion__API-*`는 **남의 워크스페이스**일 수 있으니 쓰기 전에 이름을 확인한다.
- **팀스페이스에 만든다. 개인 페이지 · draft로 만들지 않는다.** `notion-get-teams`로 팀스페이스 ID를 찾고,
  `notion-create-pages`의 parent를 `{"teamspace_id": ...}`로 줘서 팀스페이스 맨 위에 「프로젝트 홈」을 만든다.
  `move-pages`로는 팀스페이스 맨 위로 옮길 수 없으니 처음부터 팀스페이스에 만든다.
- 정해지지 않은 것은 "미정"으로 두고 진행한다. 물어볼 것은 하나씩만: 기간, 인원·역할, 문서 목록.

## 1. 홈 화면 구조

위에서부터 **대시보드 2열 → 협업 흐름 한 줄 → 규칙 토글 → 영역별 문서 3×2 → 탭으로 묶은 보기**다.
틀 전체와 그대로 복사할 수 있는 마크업은 `references/home-layout.md`에 있다. 홈을 새로 만들거나
기존 홈이 "어지럽다"는 말을 들었을 때 그 파일을 먼저 읽는다.

지키는 원리만 여기 적는다. 모양이 달라져도 이 네 가지는 같다.

1. **상단 박스는 가로로 나눈다.** 현황(기간·단계·주제·팀)과 링크(깃허브·슬랙·배포·API)를 2열로.
   세로로 쌓으면 첫 화면이 전부 박스가 된다. 문서 버전 규칙처럼 평소 안 봐도 되는 안내는 토글로 접는다.
2. **영역 카드는 열 수를 통일한다.** 3열 + 2열로 나누면 두 번째 줄 칸이 1.5배로 넓어져 격자가 깨진다.
   영역이 5개면 여섯 번째 칸(Records: DB 원본 링크)을 만들어 3×2로 맞추고 `ratio`를 명시한다.
3. **같은 DB를 위아래에 두 번 넣지 않는다.** 위 카드에는 원본 링크, 아래에는 연결 보기 — 역할을 나눈다.
4. **연결 보기는 `<tabs>`로 묶는다.** 전체폭 보기를 네 개 세로로 쌓으면 페이지가 끝없이 길어진다.

커버는 노션 기본 이미지도 되고 Unsplash 직접 주소도 된다. 커버는 가로로 길게 잘리고 그 위에 제목이
얹히므로 **무늬가 적고 어두운 쪽**을 고른다. 후보는 `?w=760&h=200&fit=crop`으로 열어 커버 비율에서
어떻게 보이는지 확인한 뒤 보여 준다. 새 주소는 `curl -I`로 200인지 먼저 본다.

## 2. 데이터베이스 3개

`notion-create-database`에 SQL DDL로 만든다. 상태는 칸반 사진과 같은 영어 이름.

```sql
-- 할 일 보드
CREATE TABLE ("할 일" TITLE,
  "상태" STATUS('To Do':gray:to_do, 'In Progress':blue:in_progress, 'Review':yellow:in_progress, 'Done':green:complete),
  "역할" SELECT('PM':purple, 'FE':pink, 'BE':red, '데이터 A':blue, '데이터 B':yellow, 'AI A':green, 'AI B':orange, '전원':gray),
  "단계" SELECT(...), "담당자" PEOPLE, "마감일" DATE, "우선순위" SELECT('높음':red, '보통':yellow, '낮음':gray),
  "산출물" RICH_TEXT, "이슈·PR" URL, "번호" UNIQUE_ID PREFIX 'ML')
-- 실험 기록 (ML 프로젝트일 때)
CREATE TABLE ("실험명" TITLE, "날짜" DATE, "담당" PEOPLE, "역할" SELECT(...), "모델" SELECT(...),
  "데이터셋 버전" SELECT('v1':blue), "피처 버전" RICH_TEXT, "검증 점수" NUMBER,
  "결과" SELECT('채택':green, '보류':yellow, '기각':red), "비고" RICH_TEXT, "번호" UNIQUE_ID PREFIX 'EXP')
-- 일일진행일지
CREATE TABLE ("제목" TITLE, "날짜" DATE, "단계" SELECT(...), "작성자" PEOPLE,
  "오늘 한 일" RICH_TEXT, "내일 할 일" RICH_TEXT, "막힌 점" RICH_TEXT)
```

보기(`notion-create-view`, 문법은 `notion://docs/view-dsl-spec`):
- 할 일 보드 탭: `칸반 (역할별 줄)` = `GROUP BY "상태" BY OPTION SHOW EMPTY; SUB GROUP BY "역할"`,
  `내 할 일` = `FILTER "담당자" = "me"`, `단계별` = `GROUP BY "단계"; CARD LAYOUT compact`
- 실험 기록: `리더보드` = `SORT BY "검증 점수" DESC`
- 일지: `달력` = `CALENDAR BY "날짜"`
- 홈에 붙이는 보기는 `parent_page_id`로 만들고 `show_data_source_title: false`.
  진행 현황 = `GROUP BY "단계"; CHART bar AGGREGATE count STACK BY "상태" COLOR colorful`
  (무료 플랜은 차트 1개까지일 수 있다).

## 3. 문서 — 정해진 것만, 짧은 틀로

문서를 고르는 기준 3가지 (사용자와 논의해 정함):
1. **최종 보고서의 한 장이 되는가** — 안 들어가면 만들지 않는다
2. **책임 역할이 하나인가** — 여러 역할이 조금씩 쓰는 문서는 아무도 안 쓴다
3. **프로젝트의 중심(ML이면 데이터 · 모델)이 문서에서 드러나는가** — 웹 문서가 많고 모델 문서가 묻히면 안 된다

그리고 **계획은 계획 문서에, 결과는 처음부터 최종 보고서의 자기 장에** 쓴다("결과서"를 따로 두면 보고서와 겹친다).
ML 프로젝트 기본 6장 (10장 → 6장으로 줄여 확정한 구성):

| 문서 | 책임 | → 보고서 |
|---|---|---|
| 프로젝트 수행 계획 | PM | 1장 배경 · 목표 |
| 데이터 명세서 (변수 사전 + 정리 과정 + 데이터셋 버전 + 파생변수 · 누수 칸) | 데이터 A | 2장 데이터 |
| 분석계획서 (문제 정의 · 검증 기준(PM) · EDA에서 볼 것 · 모델링 힌트) | 데이터 B | 3장 분석 |
| 모델링 계획서 (모델 후보 · 실험 순서 · 피처 아이디어 · 고르는 기준 · 모델 넘기기) | AI A · B | 4장 모델 · 결과 |
| 웹사이트 명세 (기능 · 화면 · API · 기술 스택 · 구조 · 화면 캡처 목록) | FE · BE | 5장 웹사이트 |
| 최종 보고서 (장마다 담당, 3일차부터 직접) | 전원, 다듬기 데이터 A | — |

+ 표(문서 아님): 할 일 보드 · 실험 기록 · 일일진행일지. + 안내: 팀원 안내 · GitHub 컨벤션.
문서를 합치거나 이름을 바꿀 때 옛 페이지는 지우지 말고 홈 아래 「보관함 (이전 문서)」으로 `move-pages`해 두고, 어디로 합쳐졌는지 한 줄 적는다.

- **프로젝트 수행 계획**에 개요 · 역할 표 · 문서 표 · 단계 표(기간은 "가안"이라고 적기) · 협업 규칙 · 팀 약속 · 회의록 토글을 모은다.
  따로 역할분담표 · 협업 규칙 · 회의록 페이지를 만들지 않는다.
- 문서마다: 맨 위 파란 콜아웃(무엇을 적는 문서인지 + `담당 · 역할`) → 이모지 붙은 소제목 → 빈칸 표 → 맨 아래 변경 이력.
- **담당은 사람 이름이 아니라 역할 이름**(PM / FE / BE / 데이터 A …)으로 적는다. 한 사람이 여러 역할을 맡아도 역할별로 나눠 적는다.
- **문서끼리 ID로 잇는다**: 기능 F-01… → 화면 S-01… → API 엔드포인트 · 응답 필드 → 실험 번호 EXP- → DB `model_version`.
- 그림이 필요하면 ```` ```mermaid ```` 코드 블록(시스템 구조 flowchart, ERD erDiagram).
- 변경 이력 표:

```
---
## 📝 변경 이력
| 버전 | 날짜 | 작성자 | 수정 사항 |
|---|---|---|---|
| v0.1 | YYYY-MM-DD | PM | 초안 (틀 작성) |
```

## 4. 칸반 카드와 일지 미리 채우기

- 카드는 **역할당 2~3장, 전체 15~20장**만. 처음에 29장을 만들었다가 "쓸데없는 카드가 많다"는 말을 들었다.
  10분짜리 확인(예측값 대조, 연결 테스트), 문서 하나 쓰기, 채널 만들기처럼 작은 일은 카드로 만들지 않고
  관련 카드 안에 넣는다. 제목 앞에 이모지, `산출물`에 어느 문서에 결과를 적는지.
  지금 바로 할 0단계 카드만 담당자를 사용자로 넣어 「내 할 일」에 보이게 한다.
- 일지는 기간 안 **평일**만 센다. 공휴일도 확인한다.
  `python -c "import datetime as d; ..."`로 날짜를 뽑고, 제목 `N일차 일일진행일지 (MM/DD 요일)`,
  아이콘 `1️⃣`~`9️⃣`, 본문은 역할별 데일리 스크럼 표(오늘 한 일 / 내일 할 일 / 막힌 점) + 오늘 결정한 것 + 내일 우선순위.
  마지막 날 일지에는 마무리 체크리스트.

## 5. 팀원 붙이기 — 내부 통합 토큰

**게스트는 OAuth 방식 Notion MCP를 못 붙인다.** 노션 공식 문서에 "Only workspace members can
connect Notion MCP"라고 적혀 있고, 플랜을 올려도 안 되는 멤버십 규칙이다. 그래서 팀원이 각자
Claude로 이 노션을 읽게 하려면 소유자가 **내부 통합**을 만들어 토큰을 나눠 주는 방식이어야 한다.

절차·권한 선택·검증·공지문은 `references/team-access.md`와 `references/slack-notice.md`에 있다.
여기서 꼭 기억할 것은 세 가지다.

- **「프로젝트 홈」 한 곳만 연결하면 하위가 전부 상속된다.** 이 연결을 빼먹으면 토큰은 멀쩡한데
  접근 가능한 문서가 0건이 된다. `claude mcp list`에는 ✓ Connected로 떠서 제일 헷갈리는 실패다.
- **토큰은 채팅에 붙이게 하지 말고 파일로 받는다.** 스크래치패드처럼 git 저장소 밖에 두고,
  `scripts/verify_notion_integration.py <토큰파일> <홈페이지ID>`로 무엇이 보이는지 확인해 준다.
  쓰기까지 보려면 `--write <할일보드ID>`(테스트 카드를 만들었다 바로 지움) — 실제 변경이니 먼저 묻는다.
- **편집 이력이 전부 통합 이름으로 찍힌다.** 누가 썼는지 노션에 안 남으니, 일지·실험 기록의
  담당 칸을 본인 이름으로 채우라고 공지에 넣는다. 프로젝트가 끝나면 통합 삭제가 곧 전원 차단이다.

## 6. 점검 — "다 맞는지 봐줘"

홈과 문서 전부를 `notion-fetch`로 읽고 카드는 `notion-query-data-sources`(rows 모드)로 읽은 뒤 아래를 본다.
고치기 전에 찾은 것을 번호 목록으로 먼저 보여 준다.

- 담당 표기가 역할 이름으로 통일됐는지 (사람 이름이 남은 문서)
- 같은 일을 두 문서가 다른 사람에게 맡기지 않았는지 (예: 분할 파일을 파이프라인은 데이터, 카드는 PM)
- 기능 ID · 화면 ID · API 연결 칸이 비어 있지 않은지, 선택 기능을 하면 무엇을 더 만들어야 하는지 적혔는지
- 수행 계획의 단계 · 기간 · 역할과 카드의 단계 · 역할 · 산출물 문서 이름이 맞는지 (문서를 합치거나 이름을 바꾼 뒤 특히)
- 모든 문서에 변경 이력이 있는지
- 코드 블록 언어가 엉뚱하게(javascript) 붙지 않았는지
- 이름 없는 빈 카드 · 빈 행이 있는지

고친 문서는 **변경 이력에 버전을 올려** 무엇을 왜 고쳤는지 한 줄 남긴다.
화면 모양은 직접 볼 수 없으니 "구조만 확인했다, 화면은 열어서 확인해 달라"고 말한다.

## 노션 도구 함정 (실제로 겪은 것)

- **데이터베이스를 만들면 이름 없는 빈 행이 생길 수 있다.** 점검 때 찾아서 사용자에게 보여 주고,
  지워도 된다고 하면 `notion-delete-pages`(`user_confirmed: true`)로 휴지통에 옮긴다. 묻지 않고 지우지 않는다.
- **선택지를 바꿀 때 `ALTER COLUMN ... SET SELECT(...)`는 목록에 없는 옵션을 지우고, 그 값을 쓰던 카드도 비운다.**
  순서: 새 옵션을 옛 옵션과 함께 추가 → 카드를 새 옵션으로 옮김 → 옛 옵션을 쓰는 카드가 0장인지 조회 → 옛 옵션 삭제.
- **`replace_content`는 기존 하위 페이지 · 데이터베이스 태그(`<page url=...>`, `<database url=...>`)를 그대로 넣어야 한다.**
  새 하위 페이지는 `<page>제목</page>`(url 없이)로 만들 수 있다. 빼면 지워지니, 일부러 지울 때만 `allow_deleting_content`를 쓰고 무엇이 빠지는지 먼저 말한다.
- 표는 `| --- |` 형태로 저장된다. `update_content`의 `old_str`은 반드시 fetch한 그대로 복사한다.
- **`<mention>`이나 `<image source="notion-file-block://...">`가 들어간 부분은 `update_content`로 찾지 못한다**(fetch한 그대로 넣어도 no match). 그 부분을 바꿔야 하면 페이지를 fetch한 뒤 `replace_content`로 통째로 다시 쓴다. 다른 그림은 fetch에 나온 `<image source=...>` 태그를 그대로 두면 유지된다.
- 사용자가 노션에서 직접 고친 내용이 있을 수 있으니, 고치기 전에 항상 다시 fetch하고 그 내용 위에 덧붙인다.
- 코드 블록은 언어를 안 주면 javascript로 저장될 수 있다. 양식 · 템플릿은 ```` ```plain text ````로 쓴다.
- 홈에 붙이는 연결 보기는 페이지 맨 끝에 붙는다. 소제목을 `insert_content`(end)로 먼저 넣고 바로 `create-view`를 하는 순서로 쌓는다.
- 노션 템플릿 갤러리 템플릿은 API로 복제할 수 없다. 참고만 하고 직접 만든다.
- **홈을 통째로 다시 짤 때는 `replace_content` 한 번으로 한다.** 하위 페이지·DB 태그와
  연결 보기의 url을 fetch한 그대로 옮기면 블록이 이동만 되어 보기 설정(칸반 모양, 차트)이 유지된다.
  url을 새로 비우면 빈 보기가 다시 만들어진다.
- **`<tabs>`/`<tab>` 안에도 연결 보기를 넣을 수 있다.** 탭 제목은 여는 태그 다음 줄의 본문이고,
  자식 블록은 빈 줄 뒤에 온다. 여는·닫는 태그에 붙는 빈 줄은 군더더기 공백이 되니 넣지 않는다.
- **`<column>`에 `ratio`를 주지 않으면 줄마다 너비가 달라진다.** 두 줄 이상 격자를 만들 때는
  모든 줄에 같은 `ratio`를 명시한다.
- 화면 모양(탭이 제대로 보이는지, 커버가 어떻게 잘리는지)은 도구로 확인할 수 없다.
  구조만 확인했다고 말하고 사용자에게 열어 보라고 한다.

## 스타일

- 이모지 · 커버 사진으로 꾸미되 **단순하게**. 문서는 빈칸 틀 위주로 짧게, 설명 문장은 콜아웃 한 줄로.
- 사용자에게 보고할 때는 한국어, 쉬운 말. 무엇을 만들었는지 · 무엇을 확인 못 했는지를 나눠서 말한다.

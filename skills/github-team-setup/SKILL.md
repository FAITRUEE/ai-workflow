# GitHub 팀 협업 체계 깔기

팀 프로젝트를 시작할 때마다 같은 것을 깔았다 — 낙상 감지(3개 저장소), 온점(3개),
눈치(조직 + 3개), 스터디 매칭 서비스. 처음 하루에 깔아 두면 나머지 기간에 "이 PR 뭐였지"가 사라진다.

## 1. 구조

- **조직 하나 + 영역별 저장소**: `AI` · `BE` · `FE` (+ 필요하면 `docs`).
- 조직에 **`.github` 저장소**를 만들면, 자기 템플릿이 없는 저장소 전부에 PR · 이슈 템플릿이 자동으로 적용된다.
  조직 첫 화면 소개는 `.github/profile/README.md`.

## 2. 브랜치 규칙

| 브랜치 | 쓰임 | 자동 라벨 |
|---|---|---|
| `feat/…` | 기능 · 실험 코드 | `enhancement` |
| `fix/…` | 버그 | `bug` |
| `docs/…` | 문서 | `documentation` |
| `refactor/…` | 구조 정리 | `refactor` |
| `data/…` | 데이터 처리 | `data` |

- `main`은 PR로만. **squash 병합**으로 PR 하나 = 커밋 하나.
- AI가 작업할 때도 같다 — 브랜치 → PR까지만 올리고, **병합은 사람이 한다.**

## 3. 깔 파일 (`templates/`에 그대로 있음)

| 파일 | 위치 |
|---|---|
| `labeler.yml` | 저장소마다 `.github/labeler.yml` |
| `labeler-workflow.yml` | 저장소마다 `.github/workflows/labeler.yml` |
| `pull_request_template.md` | 조직 `.github` 저장소 루트 |
| `ISSUE_TEMPLATE/task.md` | 조직 `.github` 저장소 |

PR 템플릿은 **무엇을 · 왜 / 어떻게 확인했나 / 알려진 한계 / 관련 / 체크** 다섯 칸이다.
"어떻게 확인했나"를 빈칸으로 못 두게 하는 게 핵심이다(`assumption-check`와 같은 원리).
체크 칸에는 **원본 데이터 · 모델 파일 · 키(.env)가 커밋에 없다**를 맨 위에 둔다.

## 4. 리뷰 방식

리뷰 댓글은 세 갈래로 나눠 쓴다. 받는 사람이 무엇부터 고칠지 바로 안다.

- **[필수]** 병합 전에 고쳐야 함
- **[권장]** 고치면 좋음
- **[의견]** 생각해 볼 거리

## 5. 확인

- 테스트 PR을 `docs/…` 브랜치로 하나 열어 라벨이 붙는지, 템플릿이 뜨는지 본다.
- `pull_request_target`은 포크 PR에서도 쓰기 권한으로 돈다. 라벨 붙이기 외의 일을 이 워크플로에 넣지 않는다.
